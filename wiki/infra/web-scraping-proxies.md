# Прокси в веб-сборе данных

Прокси в data-collection pipeline — это сетевой посредник между клиентом и целевым сервисом. Он меняет исходящий IP и иногда даёт географическую, сессионную или protocol-level конфигурацию. Он **не** даёт разрешение на сбор данных, не отменяет условия сервиса и не делает доступ к защищённой странице допустимым.

Практически прокси нужен не ради «обхода защиты», а чтобы построить контролируемый сетевой путь для разрешённых сценариев: собственные сервисы, официальные API, согласованный мониторинг, публичные data feeds или ограниченный сбор, который разрешён правилами источника. Если источник отвечает `429`, CAPTCHA или block page, это сигнал снизить нагрузку, перейти на официальный канал или остановиться — не инструкция повышать маскировку.

## Что выбрать: сначала задача, потом тип IP

| Тип | Откуда IP | Сильная сторона | Ограничение |
|---|---|---|---|
| Datacenter | ASN облака/ЦОД | скорость, цена, прогнозируемая инфраструктура | многие сайты отдельно ограничивают traffic из хостинговых сетей |
| Residential | потребительские ISP ranges | география и более похожий на бытовой network context | дороже, обычно оплачивается трафик; критичны происхождение IP и согласие участников сети |
| Mobile | сети мобильных операторов | мобильная география и carrier network context | высокая цена, variable latency, жёсткие условия использования |
| ISP/static ISP | IP, зарегистрированный на consumer ISP, но размещённый в server environment | стабильная сессия без rotation | не заменяет permission и может быть дорогим при масштабировании |

Исходная статья на Habr верно выделяет, что цена сама по себе не измеряет полезность пула. Но её формулировки вроде «мобильные IP почти неубиваемы» слишком сильные. У каждого типа могут быть ограничения со стороны target, провайдера, закона и условий использования. Выбирать надо по разрешённому use case, бюджету, требуемой стабильности сессии и воспроизводимому тесту, а не по обещанию «пройти Cloudflare».

## Метрики, которые имеют смысл

`200 OK` сам по себе не означает успех: можно получить пустую страницу, страницу consent, login wall, block page или нерелевантную версию. Рабочая метрика требует явно определённого результата.

| Метрика | Как считать | Что не путать с ней |
|---|---|---|
| Valid-success rate | доля ответов, прошедших schema/content validation в разрешённом сценарии | просто HTTP 200 |
| TTFB и end-to-end latency | время до первого байта и полное время получения допустимого ответа | среднюю задержку без percentiles и ошибок |
| Block/rate-limit rate | `429`, `403`, challenge, explicit unavailable и другие отказные состояния | «плохой HTML» без классификации причины |
| IP/reputation signal | наблюдаемые отказы по IP/pool и данные репутационных баз, если они применимы | универсальный fraud score, который якобы гарантирует доступ |
| Cost per valid record | трафик + прокси + retries + browser/render cost, делённые на валидные записи | цену гигабайта в отрыве от качества |

Провайдерские claims полезны только как кандидат для проверки. В источнике приведены точные success-rate и pool-size для семи компаний, включая личное утверждение автора о `99.2%` у NodeMaven. Методика, целевые сайты, размер выборки, тайминг, правила валидации и raw logs не опубликованы. Поэтому этот рейтинг нельзя использовать как независимый benchmark или закупочное основание.

## Минимальный честный тест

Тестировать нужно только на собственных, официальных или явно разрешённых endpoint-ах. Один и тот же protocol полезен и для выбора провайдера, и для обнаружения того, что поменялся сам target.

1. **Зафиксировать разрешённый scope.** Endpoint, лимит, время, регионы, допустимые данные и критерий остановки.
2. **Собрать baseline без прокси** там, где это разрешено: latency, valid-success, response shape, limit headers.
3. **Прогнать кандидатов одинаковыми bounded batches.** Одинаковые request template, concurrency, retries и time window; не смешивать provider effect с изменением кода.
4. **Валидировать payload.** Проверять schema, обязательные поля, freshness/region и content type, а не только статус.
5. **Логировать outcome.** Время, route/provider, статус, error class, расход и нормализованный результат без секретов/PII.
6. **Принять решение по стоимости валидной записи.** Если скорость растёт, а valid-success или data quality падает, «дешёвый» маршрут дороже.

Для регулярного мониторинга полезна семантика `complete` / `blocked` / `timeout` / `drift_detected`, а не один красивый результат. В [ru-marketplace-mcp]({{ '/wiki/tools/ru-marketplace-mcp' | relative_url }}) эта граница сделана явно: отсутствие ответа источника не превращается в выдуманный ноль или абсолютный рейтинг.

## Операционная модель

Прокси — один слой среди нескольких. Надёжный легитимный pipeline разделяет:

```text
разрешённый источник/API
  → bounded client + cache + rate policy
  → выбранный network route
  → schema/content validation
  → outcome log + cost/quality metrics
  → минимизированное хранилище
```

- **Rate policy и caching** важнее rotation: сначала снизить ненужные запросы, использовать `ETag`/`Last-Modified`, incremental refresh и официальные выгрузки.
- **Сессия** нужна лишь когда это предусмотрено разрешённым workflow; не следует переносить cookies между задачами или логировать их.
- **Маршрут** должен быть наблюдаемым: уметь отличить provider outage, target rate limit, parser drift и ошибку своего кода.
- **Данные** должны быть минимизированы. Публичная страница не означает, что любые собранные персональные данные можно бесконечно хранить или пересылать; [OpenAI Privacy Filter]({{ '/wiki/tools/openai-privacy-filter' | relative_url }}) может быть отдельным PII-redaction шагом до внешней LLM или индексации.

[agent-aget]({{ '/wiki/tools/agent-aget' | relative_url }}) может быть browser-capability в разрешённом workflow, но persistent profile, cookies и stealth-compatible browser не отменяют правила target. Прокси не превращает automation в универсальный обход ограничений.

## Не путать с SSH proxy

[ASSH]({{ '/wiki/tools/assh' | relative_url }}) использует `ProxyCommand` и gateway chains для SSH-доступа к инфраструктуре. Это не residential/mobile/ISP egress proxy для web data collection. Оба класса называют «proxy», но решают разные задачи:

| Вопрос | Outbound web proxy | ASSH / SSH gateway |
|---|---|---|
| Куда идёт трафик | HTTP(S)/SOCKS-клиент → web target | SSH client → host через bastion/gateway |
| Главная цель | управляемый egress для допустимого web access | маршрутизация и конфиг SSH-доступа |
| Главный риск | abuse, ToS/compliance, data quality, расходы | потеря доступа, ключи, ошибочный `~/.ssh/config` |

## Что в исходной статье не стоит копировать

Habr-источник предлагает синхронизировать browser headers, имитировать TLS fingerprint и использовать инструменты для прохождения антибот-защит. Эти советы намеренно не превращены здесь в инструкцию: такая техника может обходить ограничения целевых сервисов. Для рабочего и устойчивого контура лучше использовать официальные API, export, партнёрский доступ, cache и лимиты, либо получить разрешение у владельца данных.

Также из статьи не следует переносить provider ranking как факт. Он субъективен, коммерческие условия меняются быстро, а опубликованной воспроизводимой методики нет. В wiki сохранён принцип выбора и проверки, не рекламный scoreboard.

## Практический вывод

Хороший proxy choice — это не «самый чистый IP», а измеряемый и разрешённый сетевой маршрут с понятной стоимостью валидного результата. Начинать нужно с legal scope, официального канала и ограниченного теста; завершать — наблюдаемостью, data validation и минимизацией хранения.

Если для задачи нужен постоянный обход CAPTCHA, подмена TLS-отпечатков или агрессивная ротация, проблема, скорее всего, не в типе прокси. Нужен другой способ получить данные: API, export, лицензия, партнёрский доступ или отказ от недопустимого источника.
